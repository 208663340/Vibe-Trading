## Important

### I1 — [P1] Do not deduplicate ID-less recovery controls using the browser's inherited Last-Event-ID

**Primary location:** `frontend/src/hooks/useSSE.ts:104–109` (tight fix anchor `:109`). Related: `:136`, `agent/src/runtime/session/events.py:35–53`, `:163–168`, `:350`, `frontend/src/pages/Agent.tsx:1187`.

The backend intentionally emits `session.resync` with `event_id=None`; serialization omits the `id:` field. Native EventSource preserves its last-event-ID buffer across frames with no `id` field, so such a MessageEvent carries the last ordinary event's ID. After any indexed event has been delivered, a queue-overflow resync therefore hits `trackEventId(raw.lastEventId)` as a duplicate. The hook first sets `damagedRef=true`, then returns before invoking the recovery handler. No authoritative hydration or replacement connection starts. Subsequent ordinary events are suppressed, and EOF hits the damaged branch at line 136 that does not schedule a reconnect. The page can remain stranded until an unrelated recovery or navigation; a later terminal may render but does not repair the missing transcript/history stream.

The same dedup boundary can swallow `session_cleared` after an ordinary indexed frame, leaving the removed session visible and reconnecting instead of applying the clear handler. This is one shared control-event classification defect, not a separate finding.

**Evidence:** an in-memory probe executed the current hook with a fake EventSource that preserves the wire last-ID buffer. Sequence: `text_delta(id=event-1)`, `session.resync(no id, latest_event_id=event-9)`, `text_delta(id=event-10)`, EOF. Observed `deltas=1`, `recovered=0`, `statusAfterError="reconnecting"`; no reconnect timer is scheduled by the damaged branch. Existing tests hide the issue: `frontend/src/hooks/__tests__/useSSE.test.ts:25–27` assigns an empty ID whenever omitted, and the new recovery test at `:427–432` sends resync before any indexed event. Page ownership fixtures likewise omit real wire ID inheritance.

**Required fix/verification:** classify ID-less control types before ordinary-event ID dedup/cursor mutation, or implement an equally explicit wire-safe distinction without moving the resume cursor to a synthetic control ID. Add a regression with an ordinary indexed event first and inherited lastEventId on resync; assert hydration handler runs and connection is replaced at the payload cursor. Cover inherited-ID `session_cleared`, retained terminal processing, and damaged EOF behavior. Preserve dedup/resume of ordinary durable events.

### I2 — [P2, mandatory O1 confirmed] Guard the SSE report GET by its start revision

**Primary location:** `frontend/src/pages/Agent.tsx:967–974`. Request starts at `:948–956`; compare the corrected history path at `:546–576` and merge helper `frontend/src/features/agent/history.ts:37–50`.

The completion handler retains view/operation ownership but does not capture transcript revision before awaiting `getRun`. A still-current SSE report request can start first, then a later history read/enrichment for the same `report:${sid}:${attemptId}:${runId}` commits fresh metrics/equity. When the old SSE request finally resolves stale data or rejects, its token is still current because history uses a different operation category. The commit appends its stale report to the **snapshot** argument of `reconcileHistory` and passes an empty current list. The snapshot Map keeps the last duplicate unconditionally, so the older response replaces the newly committed row and receives an even newer revision. Failure replaces valid metrics/equity with an empty fallback card; a stale success replaces them with stale values. This is the reverse ordering explicitly deferred as O1 and remains present at the reviewed HEAD.

**Evidence:** the actual ES2022-transpiled history helper, given a revision-10 fresh report and the current SSE commit shape, returned only the revision-11 fallback row without metrics/equity; stale-success input returned total_return 0.1 instead of the newer 0.5. The existing guarded `mergeEnrichment` with request-start revision 8 preserved the revision-10 row in both cases. This probe demonstrates the actual merge behavior; the async ordering follows directly from separate report/history tokens. Existing page regressions at `frontend/src/pages/__tests__/AgentSessionOwnership.test.tsx` exercise old-history-GET → new-SSE-report only, not its reverse.

**Required fix/verification:** capture the entity-read start revision before SSE `getRun`, use the same revision-aware entity merge as history enrichment, and preserve existing fresh fields when an obsolete fallback arrives. Add page-level deferred tests for old SSE GET → later history enrichment → old stale success and old failure, as well as a fresh SSE success. Assert a single report row and no loss of fresh metrics/equity or already newer optional report fields.

A logically selected outcome does not make a blocked worker physically finished, and the current release predicates respect that distinction (`execution.py:120`; `run_lifecycle.py:59`).
- **Repeated close, cancelled close waiter, foreign/unknown event loop and reuse:** no new actionable loss of ownership found. The implementation reports incomplete close and retains the store claim. This review does not promise bounded physical termination of non-cooperative Python/SDK threads (`api/runtime.py:84`; `execution.py:183`).
- **Producer cancellation between initial admission and first SDK call:** considered the small scheduling window at `call_runner.py:197–204`, `:259–262`, `:299`. Once admitted, a producer can race cancellation before the waiting caller revokes its lease. The stated contract gives bounded caller cancellation and fences late observations, not a guarantee that already-admitted external provider work can never start/finish. No separate finding asserted, and no live/provider billing claim made. Worker-side pre-dispatch tightening may be useful only if the contract is strengthened explicitly.
- **Provider cleanup, empty-stream fallback and default budgets across lifespans:** examined iterator-finally, fallback revocation check, async cleanup completion retention and startup failure. No additional actionable defect identified; abandoned producer leases remain real until cleanup completion (`call_runner.py:220–253`; `chat.py:572–579`).
- **Readonly timeout/cancel, completion/refusal race, context and mutable-cache write barrier:** examined physical retired leases, worker-side stop authorization, explicit refusal, copied context, dispatch-time prepare and ordered commit. Permanently blocked readonly work intentionally consumes capacity rather than making replacement unbounded (`tool_execution.py:154`, `:193`, `:272`, `:396`).
- **Already-admitted callbacks:** `RunLifecycle.emit` deliberately releases its gate before invoking a callback (`run_lifecycle.py:50–57`). - **Physically unwritable artifacts and atomic state:** `_persist_terminal` logs artifact-write failure and retains the chosen outcome (`loop.py:1462`); it cannot guarantee persistence on unwritable media. - **Initialization exceptions before an owned ChatLLM enters its cleanup try block:** considered the construction sequence in `service.py:528`; no concrete newly introduced leak was established in this diff, and earlier construction behavior is not promoted into a speculative new blocker.

- **Search store binding / multiple independent stores:** considered shared index/store coupling at the changed search seam. No concrete introduced cross-store corruption was established; production multi-process/multi-worker shared-writer safety remains explicitly outside this single-process design.
- **Legacy imports/facades and Python 3.11:** inspected compatibility-oriented changes and syntax, with parent static-gate evidence noted above. Did not execute a second environment or claim third-party SDK compatibility beyond the reviewed fake/recorded regression boundaries.
