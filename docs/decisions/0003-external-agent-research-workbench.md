# ADR-003: External Code Agent 驱动的本地量化研究工作台

Status: 产品方向已确认；M0 已实施验收，首批旧助手前端与品牌清理已完成。M1–M3 仍为后续阶段，未实施验收。
Date: 2026-10-26（Asia/Shanghai）。
Decision process: 两轮 grilling 访谈；用户先选择 Q1–Q4 的 A，再确认按 Q5–Q7 的推荐方案推进。

## Context

Vibe-Trading 已有回测、因子、数据加载、研究记录与报告界面。新的产品目标是让独立研究者使用外部 Codex 等 Code Agent 编写和迭代策略，平台承担实验执行、分析、验证和归档。

本轮交付整体方针，后续按阶段拆实施任务。已有研究计算基础优先复用；清理工作围绕明确的产品边界进行。判断依据为当前工作区的静态代码与文档走查，不代表完整运行验收。

## Decision

### 1. 产品承诺与主流程

产品定位：**面向 Code Agent 的本地量化研究工作台。**

对外承诺：让研究者更快定位策略问题，比较修改是否有效，并保留可复核的实验依据。

主流程：

```mermaid
flowchart LR
    A[外部 Agent 编写策略] --> B[提交实验配置与代码]
    B --> C[执行与产物校验]
    C --> D[收益／回撤诊断]
    D --> E[修改并生成新版本]
    E --> F[同口径对照]
    F --> G[稳健性与样本外验证]
    G --> H[保留或淘汰并记录依据]
    D --> A
```

研究结果允许是淘汰策略、数据不足或证据不足。保留原因与失败实验是研究成果的一部分。

### 2. 外部 Agent 与平台的职责

| 外部 Code Agent | 平台研究服务 | Web 工作台 |
| --- | --- | --- |
| 理解目标、查资料、提出假设 | 数据目录、快照引用与覆盖检查 | 研究项目与实验历史 |
| 编写策略和实验配置 | 输入校验、任务执行、状态与日志 | 执行进度与错误定位 |
| 根据结果修改策略 | 统一指标计算、诊断与验证计算 | 图表、交易、持仓与区间联动 |
| 撰写解释与研究结论 | 保存代码、参数、产物、来源与父实验 | 版本差异、实验对比与导出 |

平台计算与报告浏览不依赖 LLM 凭证。用户的外部 Agent 会话结束后，项目与实验仍可独立检索。

研究服务通过 CLI、MCP 和 HTTP 提供同一套能力；Web 与外部 Agent 读取相同的计算结果与状态。先交付稳定的本地 CLI／JSON 与产物协议，再用薄适配层开放 MCP。接口名称与具体字段在实施任务中确定。

一期需要的外部操作包括：创建或选择项目、检查数据与配置、提交实验、查询状态、读取诊断和产物、对照实验、取消任务、导出实验包。长任务由平台管理，提交后返回稳定 ID；终端断线或 Agent 退出不改变任务所属关系。

### 3. 核心研究对象与产物协议

沿用现有文件与 SQLite 基础，收敛对象关系：

`研究项目／假设 → 策略版本 → 实验运行 → 诊断与验证产物`

策略可以产生多个实验；策略变更产生新版本；执行重试保留 attempt 关系。显示名称、评论与标签可以编辑，已完成实验的输入与原始结果保持不变。

每次运行保存：

- 项目、策略版本、父实验与修改说明。
- 实际执行代码的快照与指纹，包括所依赖的项目源码；记录外部依赖版本。
- 完整配置、入口、运行环境、随机种子（适用时）。
- 数据内容指纹、可读取的快照位置、日期覆盖、股票池、复权和时区等口径。
- 基准、资金、费用、滑点、仓位约束、交易时点与交易规则。
- 真实执行状态、日志、原始产物、平台计算结果与检查发现。

数据哈希只能用于识别内容。可复跑还要求保留可读取的数据快照或可恢复的确定版本；仅记录一个会被覆盖的 CSV 路径不算完整复现。数据和凭据保持在用户本地，导出包明确列出包含的文件与需要自行提供的数据。

产物采用有版本的协议，按可用数据启用分析：

| 产物层次 | 输入 | 可提供的分析 |
| --- | --- | --- |
| 基础 | 净值、时间、初始资金、资金流口径、实验配置 | 收益、回撤、风险统计与曲线比较 |
| 交易 | 成交／平仓记录、数量、价格、费用、信号或交易标识 | 交易分布、持有期、交易定位与修改前后差异 |
| 持仓与估值 | 逐期仓位、现金、估值价格、费用及资金流 | 持仓贡献、已实现与未实现变化、净值核对 |
| 验证 | 分割区间、训练与选择配置、冻结参数、子实验结果 | 稳健性、滚动样本外与选择过程复核 |

协议应区分订单、成交和已平仓交易。零成交、期末仍持仓、缺少某类明细都是合法且可说明的状态；按实际输入降级分析，不补造数据。

### 4. 证据边界

每份结果分别展示三类信息，避免用单个可信度分数替代事实：

1. **执行来源**：外部导入、自定义程序由平台执行、平台内置引擎执行。
2. **已完成的检查**：格式与数值检查、根据净值重算指标、依据明细核对账户变化等。
3. **研究验证范围**：样本内、分段分析、样本外、参数扰动、成本压力等，以及缺失项。

平台重算指标不证明自定义成交逻辑正确；内置引擎执行也不自动证明数据无偏差或未来有效。用户能从每个结论定位到实际计算与产物。

诊断先输出事实与可检查的差异。策略为什么失效的经济解释由研究者或外部 Agent 提出，并与下一轮实验关联。`reason` 等外部程序文字标注应保留来源。

### 5. 前端的信息结构

第一阶段以“项目—实验—诊断—对照”为主导航关系：

- 首页展示最近项目、运行中实验、失败或待复核事项。
- 项目页展示研究假设、基线、策略版本与全部实验。
- 实验详情复用 RunDetail 的图表、交易、持仓、运行卡和代码视图，逐步整合成稳定的诊断流程。
- 对照页展示输入差异、可比性、曲线差异和交易／风险变化。
- 数据与设置保留本地路径、数据来源、运行预算和外部接入配置。

因子库继续作为研究资源保留，后续接入统一实验。独立策略库可先作为项目内的版本视图，避免同时建设多个重复目录。

主操作包括查看诊断、选择基线、创建对照实验、重跑固定配置、取消任务、导出实验包、复制结构化上下文给外部 Agent。

## Cleanup Boundaries

| 分类 | 范围 | 执行原则 |
| --- | --- | --- |
| 保留并复用 | `backtest/`，`research/local_quant/`、`factors/`、`quantlib/`、`hypotheses/`、`strategy_store/`、`strategy_discovery/`，运行与产物存储，研究图表 | 先确认现有行为与测试，围绕主流程补齐缺口 |
| 先抽离共享能力 | `runtime/tools/` 中数据与研究业务，工具契约、进度事件、研究目标与 skill 文档加载，API 生命周期 | 业务实现独立于聊天会话、模型 provider 和 AgentLoop；CLI／MCP／HTTP 复用 |
| 删除候选 | 内置聊天页、全局会话侧栏、Agent store、模型设置、内部 AgentLoop、providers、Swarm、聊天 memory、聊天渠道与交互式聊天 CLI | 在调用方迁移与替代路径验收后，删除入口、实现、测试和专用依赖 |
| 移出产品范围 | 实盘下单与账户执行控制、券商交易授权、聊天型定时研究、内部自主研究编排 | 行情读取等共享能力先拆分；固定配置重跑由实验服务承担；历史用户数据保留 |
| 保留但后置 | 因子挖掘完整流水线、其他市场与复杂衍生品、持续模拟观察 | 已有可复用计算模块按依赖保留，入口不占主流程；后续按真实需求投入 |

删除顺序为：建立纯研究调用路径 → 验收外部 Agent 闭环 → 迁移入口与调用方 → 删除废弃代码与专用依赖 → 更新文档与安装检查。

每批清理以具体模块和反向依赖为单位。`runtime` 目录同时包含研究能力，不能作为一个整体删除。桌面壳、渠道、交易和数据连接器等边界均按实际用途判断，不按名称归类。

保留历史实验、策略源码和用户数据。删除助手功能不等于清空用户的会话数据库或运行目录；旧报告提供读取或显式迁移路径。旧聊天命令和内部会话 API 可在新主线中退出支持。

## Delivery Sequence

### M0：外部 Agent 独立使用与第一批清理

目标：在无平台 LLM 配置的环境中完成一次提交、执行、读结果和 Web 查看。

工作重点：独立研究服务与工具注册，研究 API 生命周期，CLI／MCP 适配，首页与全局布局去会话依赖，稳定实验 ID 与输入快照。优先复用现有本地量化路径和 program 路径。

任务系统保存提交、运行、取消中及终态，明确服务重启后的中断状态；先支持查询和显式重试。未知执行结果先核对产物与状态，重试生成新的 attempt。后台任意 Python 的中途续跑不属于默认保证。

验收：

- 无模型凭证时，研究服务、CLI、MCP 和 Web 的核心路径可用。
- 外部 Agent 提交一个已有策略，获得实验 ID，Web 显示真实状态、日志和报告。
- Agent 断开后，平台仍能管理已接收的任务；服务重启后能找回记录并识别中断。
- 支持失败、超时、零成交和数据不足，旧实验仍可读取。
- 关闭助手入口后，前端不再请求聊天会话，研究调用链不初始化模型和 Swarm。

### M1：深度诊断与版本对照

目标：研究者能回答“哪里产生收益和损失，以及这次修改改变了什么”。

工作重点：

- 回撤区间与净值、持仓、交易联动，定位损失聚集的标的、时段和交易。
- 在明细足够时拆分净值变化中的持仓损益、费用、资金流及其他调整，并保留无法解释的差额。
- 已实现与未实现损益按一致账务口径解释；避免重复计算费用或把区间内负平仓记录之和当作回撤。
- 按可用数据提供交易分布、持有期、换手、集中度、最大有利／不利波动；缺少路径数据时明确不可计算。
- 固定基线与候选，显示代码和配置差异；同数据、同区间、同成本、同资金口径下比较。
- 输入变化作为实验因素明确展示；不可比时提示具体差异，不给误导性的统一优劣排名。
- 所有核心诊断由服务计算，同时向 Web 和外部 Agent 提供。

验收：使用可手工核对的小型数据与一个完整日频策略案例，复核净值与损益解释；修改一个有明确含义的规则，定位到新增、减少或变化的交易与风险，并保存父实验关系和修改说明。

### M2：稳健性与样本外验证

目标：区分一次回测改善与跨条件成立的研究结果。

工作重点：成本压力、参数邻域、预先指定的区间与标的检验；真正执行训练／选参、冻结参数、后续窗口测试；保存全部子实验与选择规则。标签跨区间时复用合适的 purge／embargo 组件。

验证方案在测试前保存。最终留出集被查看或用于修改后，要记录其使用情况；平台只能追踪平台内的访问和声明，不能保证外部任意程序未读取额外数据。报告明确外部程序的时点约束与未核验范围。

验收：每个滚动窗口可追溯训练输入、选定参数和后续测试结果；执行成功与验证是否满足预设标准分别展示；失败与证据不足也形成完整报告。原有净值分段统计继续作为独立分析项目。

### M3：批量实验与候选筛选

目标：在既有诊断和验证标准下提高研究吞吐量。

工作重点：参数与实验矩阵、并发和总运行预算、持久子任务、候选比较与失败恢复。保留全部尝试，包括失败、淘汰、重复运行以及跨轮人工修改。

多重检验方法按统计对象和前提使用，记录尝试范围。因子 IC 的修正和策略收益的修正分别说明。候选先按预设约束筛选，再比较收益、回撤、换手与稳定性等维度。

验收：一组实验可中断后查回状态、对未完成项显式重试；最终结果能解释候选为何保留或淘汰，并能复跑单个候选。批量因子组合研究在此基础上后续扩展。

## Alternatives

- **保留内置 AI 助手与自主 Swarm**：用户已决定由外部 Code Agent 承担研究和编程，新主线移除相应产品与模型调用职责。
- **强制所有策略迁移到统一引擎**：会提高接入已有研究代码的成本。采用 program 协议，同时提供内置引擎路径，并明确不同结果的来源和核验范围。
- **只导入已完成报告**：保留导入的可能，但产品主流程包含可追踪的执行、复跑与版本对照。
- **先上共享服务或托管平台**：一期采用本地形态，继续复用 FastAPI、React、文件与 SQLite，按需要演进。
- **先批量搜索再完善验证**：采用诊断、验证、搜索的顺序，让增加的实验量始终有可比较和可解释的结果。
- **大规模重写计算与存储**：现有模块已经覆盖大量领域行为。以抽离共享服务、完善协议和针对性修复为主。

### 与既有决策的关系

- 本 ADR 替代 [ADR-001](0001-runtime-ownership-and-compatible-stability.md) 中“保留内部 AgentLoop 和全部旧助手契约”的产品前提。其明确资源所有者、持久化与展示分离、取消时等待真实终止等原则继续适用。
- 本 ADR 替代 [ADR-002](0002-autonomous-swarm-blackboard.md) 中继续建设平台内自主研究 peers 的产品方向。已实现的事务、任务记录或隔离经验可在确有复用价值时迁入确定性的实验服务，不以保留内部 Agent 为前提。
- [本地量化工具](../architecture/2026-10-19-local-quant-tools.md) 的研究计算与产物能力继续复用，其 Agent／Swarm 注入和工具注册方式随新接口迁移。
- 历史 ADR、设计与验证报告保留；本记录说明新的目标架构，不宣称旧实现已经被移除。

### 范围与评估

一期不建设多租户、云端计费、团队权限、内部模型路由、实盘执行和新 Agent 框架。研究市场从股票／ETF 日频案例开始，现有其他市场计算按复用价值保留。

效果评估关注首次完整实验耗时、固定输入复跑成功率、诊断与底层产物的一致性、完成版本对照的操作成本、失败实验恢复能力，以及有依据的保留／淘汰结论覆盖率。收益更高或生成更多候选本身不作为产品验收。

后续任务先落实 M0，再推进 M1、M2、M3。各阶段以真实研究闭环和检查证据验收；具体 API 命名、数据字段、测试清单和迁移步骤在对应实施任务中确定。
